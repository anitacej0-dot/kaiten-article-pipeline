| Проблема | Почему это плохо | Как исправить |

| 14 сервисов нужно верно классифицировать (ATS / CRM / настраиваемая) | Если смешать классы, сравнение станет некорректным, а «недостатки» — несоответствующими классу продукта | В research по каждому определить класс и профильные функции (парсинг резюме, автопостинг, интеграции с job-бордами) по офсайту |
| Kaiten — единственная в списке настраиваемая система, а не профильная ATS | Может читаться как «белая ворона» или, наоборот, как реклама | Держать единый объём/тон карточки, честные минусы; в определении заранее ввести оба класса решений, чтобы Kaiten не выглядел случайным |
| Тема заезжена — риск низкой уникальности | Много конкурентных подборок (potok, weeek, kp, kontur) + риск совпасть со своей старой статьёй | Оригинальные формулировки, не копировать источники, не повторять боилерплейт; прогон text.ru ≥75% |

## 5. Проверка gates

### Gate 1. Боль — passed
Боль не одним словом, есть сценарии и последствия для трёх ролей; переиспользована из реальной статьи.

### Gate 2. Угол — passed
Есть главная рамка (два класса решений + выбор под процесс), связана с болью и продуктовой логикой, отличает от выдачи.

### Gate 3. Формат подачи — passed
Формат выбран и обоснован, креатив 2 адекватен утилитарному интенту.

### Gate 4. Структура — passed
Порядок от логики читателя (контекст → классы решений → сервисы → таблица → выбор); для каждого блока задана задача. Точка внимания — не дать блоку «что такое CRM для HR» разрастись (в брифе предупреждено).

### Gate 5. SEO — passed
Ключи по смыслу и подзаголовкам; title/description/slug/мини-описание согласованы; таблица уместна.

### Gate 6. Продуктовая связка — passed
Kaiten через логику «наём внутри рабочих процессов», не рекламой; обязательные ограничения (нет парсинга резюме/автопостинга); указано, где Kaiten не нужен.

### Gate 7. Фактура — passed
Требования к фактам по каждому сервису, идеи таблиц/схемы, внутренние ссылки, полный перечень на проверку в research.

### Gate 8. Анти-паттерны — passed
9 конкретных запретов под тему, учтены слабые паттерны (лонгрид вместо подборки, боилерплейт, нейрослоп, переспам).

## 6. Что нужно доработать в брифе
Существенных доработок для APPROVED не требуется. На research (задачи следующего этапа):
1. По каждому из 14 сервисов определить класс (ATS / CRM / настраиваемая) и профильные функции (парсинг резюме, автопостинг, интеграции с job-бордами) по офсайту, с датой.
2. Собрать тарифы, бесплатный тариф/триал, on-premise, реестр ПО, оплату из РФ.
3. Сверить Kaiten по faq-ru.kaiten.site (шаблон CRM для подбора, бесплатный тариф, триал, коробка, реестр) и подтвердить кейс миграции с AmoCRM, если используем.
4. Проверить живость внутренних ссылок.

## 7. Точечные предложения
- **Угол:** в определении сразу назвать оба класса решений, чтобы Kaiten как настраиваемая система не выглядел исключением, а был одним из ожидаемых вариантов.
- **Структура:** блок «что такое CRM для HR» — строго 3–4 абзаца + таблица, без ухода в how-to по Kaiten (это ошибка исходной статьи).
- **Продуктовая связка:** Kaiten Встречи здесь ни при чём — не тащить; связка только через воронку найма и связь карточки кандидата с задачами.
- **Визуал:** схема «тип команды → класс решения» — самый полезный визуал, у конкурентов его нет.
